## Work Completed

### Speech-Recognition Dataset

The ten selected phrases were recorded under three conditions: quiet, distance and moderate background noise. This produced a common dataset of 30 `.m4a` recordings for each candidate service.

The recordings included 27 intended voice commands and three negative controls. The `go_to_sleep` files intentionally contain the phrase **"Go to sleep"** without the name MO because the omission occurred during recording. These files were treated as valid sleep-command samples rather than transcription errors. The negative-control recordings remained separate and were used to verify that ordinary speech would not activate an approved command.

### Primary Service Selection

Groq with `whisper-large-v3-turbo` was selected as the primary cloud speech-to-text service for Project MO V1. It combined perfect functional accuracy in the recorded dataset with low average response time and a straightforward Python integration.

Deepgram Nova-3 remains the preferred backup candidate. AssemblyAI remains a documented alternative, but its measured response time makes it less suitable for responsive V1 interaction.

This decision was documented separately in **DL-011 — Selection of Groq as the Primary Speech-to-Text Service**.

### Transcript Normalization and Command Parser

The file `tools/voice/command_parser.py` was created to keep transcript processing separate from speech recognition and command execution.

The parser:

- Converts transcripts to lowercase.
- Removes surrounding punctuation and repeated whitespace.
- Normalizes the recognized name variant `moe` to `mo`.
- Normalizes the number `15` to `fifteen`.
- Matches only approved complete command phrases.
- Returns `UNKNOWN` when no approved phrase matches.

The current command identifiers are:

- `GREETING`
- `SLEEP`
- `WAKE_UP`
- `STATUS`
- `HAPPY_FACE`
- `PLAY_SOUND`
- `SET_TIMER_15_MINUTES`
- `UNKNOWN`

The parser test suite contained 15 cases. All 15 tests passed, including alternate greetings, punctuation and capitalization differences, expected speech-to-text variations, and unrelated phrases.

### Groq-to-Parser Integration

The first Groq command-pipeline test connected a prerecorded audio file to the new parser. The verified path was:

1. Load the `.m4a` recording.
2. Send the recording to Groq.
3. Receive the transcript.
4. Normalize the transcript.
5. Identify the approved command.

The test recording was transcribed as `Mo, play a sound.` and correctly mapped to `PLAY_SOUND`.

### Stateful Command Handler

The file `tools/voice/command_handler.py` was created to manage MO's runtime state and convert detected commands into actions and responses.

The handler starts in the awake state. The `SLEEP` command changes the state to sleeping. While sleeping, normal commands are recognized by the parser but are rejected by the handler and converted to the action `NONE`. The `WAKE_UP` command remains available and restores the awake state.

The handler also maps accepted commands to actions for the future display, speaker, timer and system layers. A ten-case state test verified greetings, status, sleep, rejected actions while sleeping, wake-up behavior, sound playback, timer behavior and unknown-command handling. All 10 tests passed.

### Simulated Hardware Interface

The file `tools/voice/hardware_interface.py` was created as a boundary between software decisions and future physical hardware control.

The current interface simulates hardware commands and assigns each valid action to a target:

| Action | Simulated target |
| --- | --- |
| `GREETING` | Speaker |
| `SHOW_STATUS` | Display |
| `SHOW_HAPPY_FACE` | Display |
| `PLAY_SOUND` | Speaker |
| `START_TIMER_15_MINUTES` | Timer |
| `SLEEP` | System |
| `WAKE_UP` | System |

`NONE` does not produce a hardware command, and unsupported actions are rejected. The hardware-interface test suite contained nine cases, and all nine passed. Its command history also confirmed that only valid executed actions were stored.

### Complete Audio-to-Hardware Pipeline

The final integration test connected all completed software layers:

`Prerecorded audio → Groq transcription → command parser → command handler → simulated hardware interface`

The verified sequence was:

1. `go_to_sleep.m4a` produced `SLEEP` and placed MO in sleeping mode.
2. `play_sound.m4a` was recognized as `PLAY_SOUND`, but the handler blocked it while MO was sleeping and sent no hardware command.
3. `wake_up_mo.m4a` produced `WAKE_UP` and restored the awake state.
4. `play_sound.m4a` was accepted after wake-up and sent to the simulated speaker target.

All four end-to-end tests passed. The resulting simulated hardware history was:

```text
['SLEEP', 'WAKE_UP', 'PLAY_SOUND']
```

The missing first `PLAY_SOUND` entry confirms that the sleeping-state restriction was enforced before the hardware layer.

### ESP32 Serial Command Receiver

The firmware sketch `Project_MO_Serial_Receiver` was created in Arduino IDE and uploaded to the DOIT ESP32 DEVKIT V1 on COM3. It listens for newline-terminated action identifiers at 115200 baud and returns a structured acknowledgment in the form `ACK:<ACTION>`.

The receiver currently supports:

- `GREETING`
- `SHOW_STATUS`
- `SHOW_HAPPY_FACE`
- `PLAY_SOUND`
- `START_TIMER_15_MINUTES`
- `SLEEP`
- `WAKE_UP`

Unsupported input produces an `ERROR:UNKNOWN_COMMAND:<COMMAND>` response. After reset, the ESP32 correctly printed `MO_SERIAL_READY`, confirming that the receiver firmware had started.

### Python-to-ESP32 Serial Verification

The Python package `pyserial` version 3.5 was installed. Port enumeration detected the ESP32 on COM3.

The first direct communication test opened COM3 at 115200 baud, sent `WAKE_UP`, and received `ACK:WAKE_UP`. This confirmed the port configuration, newline termination, ESP32 receiver and acknowledgment format.

### Reusable Serial Hardware Interface

The file `tools/voice/serial_hardware_interface.py` was created to provide a reusable connection between the command handler and the ESP32.

The interface:

- Opens and closes the serial connection safely.
- Keeps one connection open while processing multiple commands.
- Allows the ESP32 startup reset to complete.
- Sends newline-terminated action identifiers.
- Checks each ESP32 response against the expected acknowledgment.
- Records only successfully acknowledged actions.
- Rejects `NONE` and unsupported actions before serial transmission.

The interface successfully transmitted `WAKE_UP`, `SLEEP`, `PLAY_SOUND` and `SHOW_STATUS` through one connection. The ESP32 returned the correct acknowledgment for all four actions, and the connection closed normally after the test.

### Complete Voice-to-ESP32 Pipeline

The final physical integration test connected every completed layer:

`Prerecorded audio → Groq transcription → command parser → command handler → serial hardware interface → physical ESP32 → acknowledgment`

The verified sequence was:

1. `go_to_sleep.m4a` generated `SLEEP`; the ESP32 received it and returned `ACK:SLEEP`.
2. `play_sound.m4a` was recognized, but the handler converted its action to `NONE` because MO was sleeping. Nothing was transmitted to the ESP32.
3. `wake_up_mo.m4a` generated `WAKE_UP`; the ESP32 received it and returned `ACK:WAKE_UP`.
4. `play_sound.m4a` generated `PLAY_SOUND` after wake-up; the ESP32 received it and returned `ACK:PLAY_SOUND`.

All four physical pipeline tests passed. The ESP32 command history was:

```text
['SLEEP', 'WAKE_UP', 'PLAY_SOUND']
```

This proves that command-state restrictions are applied before physical transmission and that accepted voice commands can travel from a recording through the cloud speech service and software layers to the real ESP32.

### Serial Reliability Improvements

The serial hardware interface was expanded so that normal connection and communication problems are handled predictably rather than causing the voice-command pipeline to freeze or terminate unexpectedly.

The updated interface now:

- Detects the ESP32 serial port automatically using common USB-to-serial device descriptions.
- Falls back to the only available serial port when exactly one port is present.
- Reports a clear error when no serial ports are available.
- Retains support for an explicitly configured port when required.
- Uses a configurable timeout and a maximum of three transmission attempts by default.
- Clears stale input before each transmission.
- Validates every response against the exact expected `ACK:<ACTION>` value.
- Retries after an empty or incorrect response.
- Attempts to reconnect after a serial communication exception.
- Records an action in command history only after a valid acknowledgment.
- Returns structured results containing execution, acknowledgment, response, attempt count and message fields.

Automatic discovery was tested with the physical ESP32 and correctly selected COM3. The `SHOW_STATUS` action was acknowledged on the first attempt. A second test was performed with the ESP32 disconnected; the interface returned a structured missing-device result with `executed: False` and the message `No serial ports were found. Connect the ESP32 and try again.` instead of crashing.

The complete voice-to-ESP32 pipeline was then repeated after reconnection. All four integration tests passed, confirming that the reliability changes did not alter speech recognition, command parsing, sleep-state enforcement or ESP32 acknowledgment behavior.

### Automated Serial-Reliability Tests

The file `tests/hardware/test_serial_reliability.py` was created with a simulated serial connection so error conditions could be tested safely and consistently without manipulating the physical ESP32 during transmission.

Five cases were verified:

1. Correct acknowledgment on the first attempt.
2. Incorrect response followed by a correct acknowledgment on the second attempt.
3. No response during all three permitted attempts.
4. Rejection of an unsupported hardware action without serial transmission.
5. Handling of `NONE` without serial transmission.

All five reliability tests passed. The retry test confirmed that an action is added to command history only after the correct acknowledgment is received, while the no-response test confirmed that three unsuccessful attempts produce a controlled failure result.

## Engineering Decisions

- Use Groq with Whisper Large V3 Turbo as the primary V1 cloud speech-to-text service.
- Retain Deepgram Nova-3 as the preferred backup candidate.
- Require an approved complete phrase match before activating a command.
- Keep transcript normalization, command identification, state handling and hardware output in separate modules.
- Maintain MO's awake and sleeping state in the command-handler layer.
- Permit only `WAKE_UP` to reactivate MO while it is sleeping.
- Convert rejected and unsupported requests to `NONE` so they cannot reach physical hardware.
- Retain the simulated hardware interface for software-only tests.
- Use a separate serial hardware interface for commands sent to the physical ESP32.
- Use newline-terminated ASCII action identifiers at 115200 baud for the initial USB serial protocol.
- Require an exact `ACK:<ACTION>` response before recording a hardware action as successful.
- Detect the ESP32 serial port automatically while retaining optional explicit port configuration.
- Keep the detected serial port open for the duration of a multi-command session and close it automatically afterward.
- Retry an action up to three times after an empty or incorrect response.
- Return structured communication errors rather than allowing missing hardware to crash the application.
- Keep API credentials in environment variables and outside the repository.

## Current Risks and Open Questions

- Speech recognition currently depends on internet access and an external service.
- The free-access conditions and limits of cloud services may change.
- The current tests use prerecorded computer audio rather than live audio from the INMP441.
- Physical display, speaker and timer actions have not yet been connected to the handler output.
- The ESP32 currently acknowledges actions but does not yet operate the display, amplifier, speaker or timer hardware.
- Port detection currently relies on common USB-to-serial description keywords or the presence of exactly one serial port.
- The current serial protocol has acknowledgments and retries but no unique command identifiers or checksum.
- Retrying after a lost acknowledgment could repeat an action that the ESP32 already performed; this should be addressed before retries control non-idempotent physical behavior.
- The final ESP32 GPIO map remains pending.
- The INMP441 still requires header soldering and an I²S audio-input test.
- The sleeping state is not retained across application or ESP32 restarts.
