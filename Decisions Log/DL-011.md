# DL-011 — Selection of Groq as the Primary Speech-to-Text Service

**Date:** 2026-09-20
**Status:** Accepted

---

## 1. Decision

Project MO will use **Groq with the `whisper-large-v3-turbo` model as the primary cloud speech-to-text service for V1**.

Deepgram Nova-3 will remain the preferred backup candidate because it produced similar response times and provides confidence scores. AssemblyAI Universal-3.5 Pro will remain an evaluated alternative, but it will not be used as the primary V1 service because its prerecorded transcription workflow produced substantially higher response times.

Before command matching, the returned transcript will be converted to lowercase, surrounding punctuation and extra whitespace will be removed, and the recognized name variant `moe` will be normalized to `mo`. Command activation will require a match against an approved command phrase rather than the presence of the word `mo` alone.

---

## 2. Context

Project MO requires speech recognition for short interaction commands such as greetings, status requests, display actions, audio playback, sleep control, wake control, and timer requests. Because this interaction should feel responsive, the selected service must combine high command accuracy with low response time and a free or low-cost development path.

Three candidate services were tested using the same set of 30 prerecorded `.m4a` files. The dataset contained ten phrases recorded under three conditions: quiet, distance, and background noise. It included 27 intended commands and three negative-control recordings designed to confirm that an ordinary sentence containing the name MO would not be treated as a command.

The phrase stored as `go_to_sleep` was intentionally evaluated as "Go to sleep" because the word "MO" had been omitted during recording. Minor formatting differences, punctuation, capitalization, the conversion of "fifteen" to `15`, and the spelling variation `Moe` were treated as correct when the intended command remained unambiguous.

Groq correctly transcribed all 27 commands and all three negative controls, producing a functional accuracy of 30/30 and an average response time of 0.607 seconds. Deepgram produced 29/30 functionally correct results and an average response time of 0.583 seconds; its only meaningful error was transcribing the noisy `Hi MO` recording as `Hi no`. AssemblyAI produced 30/30 functionally correct results with an average response time of 4.759 seconds.

---

## 3. Alternatives Considered

| Option | Test Result | Advantages | Disadvantages |
| --- | --- | --- | --- |
| **Groq — Whisper Large V3 Turbo** | 30/30 functional accuracy; 0.607 s average response time | Perfect accuracy in the test set; low latency; straightforward Python integration; suitable free development access | Did not provide a directly comparable confidence value in the test output; depends on internet access and an external service |
| **Deepgram — Nova-3** | 29/30 functional accuracy; 0.583 s average response time; 93.07% average confidence | Fastest average response; supplies confidence scores; straightforward prerecorded transcription | Failed one noisy greeting command; slightly lower functional accuracy than Groq and AssemblyAI |
| **AssemblyAI — Universal-3.5 Pro** | 30/30 functional accuracy; 4.759 s average response time; 92.97% average confidence | Perfect accuracy in the test set; supplies confidence scores; handled the noisy `Hi MO` recording correctly | Prerecorded workflow was approximately 7.8 times slower than Groq; upload-and-poll behavior is poorly suited to responsive V1 interaction |
| **Google Cloud Speech-to-Text** | Not tested | Established speech-recognition platform; command-oriented model options | Required payment-card information during account setup, conflicting with the project's preference for freely accessible testing |
| **Offline speech recognition on the ESP32** | Not tested for the full command set | Could operate without internet access and avoid cloud-service dependence | Greater memory and processing constraints; additional implementation complexity; not selected for the V1 API comparison |

---

## 4. Rationale

Groq was selected because it provided the strongest overall balance of accuracy, latency, accessibility, and implementation effort.

Accuracy is the highest-priority criterion because a small latency advantage does not compensate for a missed or incorrect command. Groq and AssemblyAI both achieved perfect functional accuracy, while Deepgram missed one greeting in the noise condition. Groq completed requests in an average of 0.607 seconds, which was only 0.024 seconds slower than Deepgram and substantially faster than AssemblyAI's prerecorded workflow.

The Groq setup also allowed the complete experiment to be performed without entering payment-card information. Its Python integration successfully processed the existing `.m4a` recordings and generated consistent results across quiet, distance, and noise conditions.

Deepgram remains a useful backup because its average response time was marginally lower and its confidence values could support rejection of uncertain transcripts. AssemblyAI demonstrated strong recognition accuracy, but its measured prerecorded latency is not suitable for the desired V1 interaction speed. Its synchronous WAV or raw PCM workflow may be reconsidered during a future hardware-based test.

---

## 5. Consequences

### Positive

* Establishes a primary speech-to-text service for V1 development.
* Provides perfect functional accuracy across the current 30-recording benchmark.
* Keeps average measured transcription latency below one second.
* Preserves Deepgram as a technically validated backup service.
* Avoids requiring payment-card information for the current development phase.
* Provides reproducible benchmark scripts and CSV results for future comparisons.
* Supports the existing English command vocabulary and `.m4a` test recordings.

### Trade-offs

* Speech recognition will depend on internet connectivity and Groq service availability.
* API credentials must be stored securely outside the source code.
* Usage limits and pricing may change and must be reviewed before wider deployment.
* The system must normalize predictable variants such as `Moe` before command matching.
* Exact approved-phrase matching is required so negative-control sentences do not activate MO.
* Results are based on recordings from one speaker and should be validated again with the final microphone, enclosure, and additional speakers.
* A future production design may require an offline fallback or local wake-word detector.
